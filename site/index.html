One address. A few questions. Your agent is in.

itda looks at the page. When the site needs a sign-in, it opens your own browser and simply watches while you use it; it never clicks or types. Then it names each thing the site can do, tries every read once, keeps what works, and connects your agent.

  1. 1

    Point

    Paste the address of a site you use. A public page is read as is; a site behind a login opens in your own browser, where you sign in and use it as usual while itda watches. What you type never leaves your computer.

    itda setup https://board.example
  2. 2

    Look it over

    itda lists what your agent will be able to do, in plain words: "List what Notices shows", "Search on Notices", "Submit the form on Notices (waits for your approval)". It tries every read once and drops what does not work.

    read get-board List what Notices shows
  3. 3

    Ask your agent

    Pick Claude, Cursor, VS Code or Codex and itda connects itself. From then on you just ask: "find this week's notices". Reads happen right away; a change stops and waits until you say yes to exactly that one.

    "use board to find this week's notices"

Built for the sites that have no API.

Sign in with your own browser

For sites with single sign-on or one-time codes, itda login --browser opens a fresh window, you sign in by hand, and only that site's session is kept in the keyring.

Old intranets welcome

Server-rendered tables become records, and forms that want a one-time CSRF token get it from a preflight step right before each approved post. The agent never sees it.

Know when a site changes

itda check runs every read that needs no input and tells you which ones no longer match, before an agent finds out the hard way. Run it on a schedule.

Safety is the default, not a setting.

Read-only by default

Every action is classified as a read or a change before it runs. Changes are off until a definition says otherwise, and then still need you.

Single-use approvals

An approval covers one request with exactly the inputs you saw, expires on its own, and is given by you, in your terminal or in a form your agent app shows you. No agent tool can approve.

Hash-chained audit log

Every call, approval and change is written to a local log where each entry seals the one before it. itda audit --verify proves nothing was edited.

Verified responses

Each action declares what a correct answer looks like. A login page, a captcha or a redesign comes back as an error with a fix, never as data.

Secrets stay put

API keys and tokens live in the OS keyring and are bound to their site's address. Agents only ever see account names.

Honest client

itda says who it is, never imitates a browser, and stops when a site refuses it. No proxy rotation, no captcha solving, no escalation.

Small, stable tool lists.

Up to 30 actions appear as one MCP tool each, with input schemas and read-only, destructive and idempotent hints. Past that, three stable tools keep the list short and prompt caches warm.

  • Same JSON envelope from MCP and itda call --json
  • Exit codes an agent can branch on: sign in, page changed, blocked, needs approval
  • Results marked untrusted and capped at 24 KB

Public APIs, ready to go.

No recording needed for these: the definitions ship inside itda, so the name is enough. Each one only talks to that site's official API, and itda check confirms every read still answers as declared.

GitHub

Repositories, issues and releases. Add a token for private repositories; opening an issue waits for you.

itda add github

npm

Packages, versions and weekly downloads. No account needed.

itda add npm

crates.io

Crates, versions and search. No account needed.

itda add crates-io

PyPI

Packages and releases with known vulnerabilities. No account needed.

itda add pypi
